# МР-1: заметки к выпуску и приёмке

Эти заметки сопровождают [эпик #13](https://github.com/PRO-Robotech/vault-operator/issues/13)
и [PR #18](https://github.com/PRO-Robotech/vault-operator/pull/18). Они предназначены
инженерам, которые обновляют установку или принимают решение о слиянии.
Состояние доказательств зафиксировано на 23 октября 2026 года. Готовность PR к review
не означает, что он уже слит в `main`, а закрытие дочерних задач не заменяет приёмку
потребителей. Слияние в `main` остаётся отдельным действием инженеров.

## Что меняется

| Область | Поведение выпуска | Что проверить при обновлении |
|---|---|---|
| Журнал VaultClaim | Намерение записывается в status до изменения Vault; неудачный патч журнала останавливает запись. Удаление политик и принадлежащих заявке ролей опирается на журнал. | Сохранность status, generation и условий; отсутствие ручной очистки журнала ради повторного reconcile. |
| Владение | Имена политик, роли, mount, Transit-ключи и префиксы проверяются на конфликт. Резервированные имена защищены; чужой mount не принимается новой заявкой автоматически. | `OwnershipConflict`, `MountConflict` и другие отказы требуют разбора владельца, а не снятия finalizer. |
| Гость | `manageConfig: false` добавляет свои политики и роли на разрешённый существующий mount, не меняя его config и не создавая reviewer в целевом кластере. | Вместе обязательны `autoCreate: false` и `rolePruning: Owned`; роли ссылаются на свои либо явно разрешённые внешние политики. |
| Шаблонные роли | `identityPaths`, функции SA и несколько `boundServiceAccounts.names` позволяют описать доступ без отдельной политики на каждую пару SA/namespace. Смена accessor вызывает перерендер. | Не смешивать `name` и `names`; проверить namespace, aliasNameSource и фактический доступ потребителя. |
| Рендер политики | Допускается закрытый набор конструкций; циклы и рекурсия отвергаются до исполнения. Rules ограничены 16384 байтами, результат — 256 КиБ. | `RenderFailed` не пишет политику в Vault. Исправить шаблон; не расширять лимиты для обхода отказа. |
| S3 create | `pendingCreate` сохраняет исходное имя, время и снимок имён до первого create. Повтор после сбоя не должен принять соседний бакет за собственный. | CRD должна сохранять весь маркер. `StatusSchemaOutdated` запрещает create до обновления схемы. |
| S3 сроки и отказы | Create имеет отдельный `--cloud-manager-create-timeout` (2m по умолчанию). `CreateRejected`, включая `CODE_RESERVED`, сохраняет намерение и использует backoff. | Согласовать сроки reconcile и вызовов; не считать истечение срока доказательством, что сервер не создал бакет. |
| S3 удаление | Created и Adopted различаются. Purge принятого бакета требует явного разрешения; неподтверждённое чужое имя не удаляется. | Retain сохраняет бакет; `DeletionBlocked` и `CreateNameMismatch` требуют проверки причины. |
| VaultSecretClaim | Generate/copy поддерживают собственный жизненный цикл KV; удаление и Retain/Purge проверяются отдельно от VaultClaim. | Проверять данные и metadata целевого leaf, сохраняя соседние leaf. Не считать произвольную ошибку чтения доказательством удаления. |
| Discovery | ShortName VaultSecretClaim изменён с `vsc` на `vscl`. | Обновить команды и скрипты. Kind, plural, singular и идентичность существующих объектов не меняются; пересоздание не требуется. |
| События и нагрузка | Повторный metadata Update Secret с тем же непустым resourceVersion отфильтровывается. Реальные изменения kubeconfig/CA и Create/Delete/Generic сохраняются. | Наблюдать ошибки, повторные очереди, стабильность лидеров и частоту reconcile с учётом числа заявок. |

## Совместимость и умолчания

Отсутствие новых полей не включает гостевой режим. Владелец mount сохраняет прежнее
удаление ролей `Exclusive` по умолчанию; `Owned` нужно выбрать явно и оно обязательно
для гостя. Существование одноимённого объекта Vault само по себе не даёт права его
принять. Не переносите журнал между заявками и не подставляйте в него чужие имена.

Ограда политик у обычных заявок по умолчанию работает в `audit`; у гостя — в `enforce`.
Переход обычной установки на `enforce` выполняется после переписи существующих правил.
Новые проверки владения и рендера могут отказать конфигурации, которую старый выпуск
применял: это намеренная граница безопасности, а не обещание принимать любую старую
конфигурацию. Поддерживаемые legacy-формы HCL сравниваются побайтово с прежним renderer.

CRD validation ratcheting позволяет изменять другие поля сохранённой заявки с прежними
значениями; это не разрешение создавать новые заявки с запрещёнными значениями.
Изменение immutable-полей требует предусмотренного жизненного цикла ресурса, а не
принудительной замены объекта. Смена shortName не требует миграции содержимого KV.

Эти заметки описывают обновление операторов на том же Vault. Перенос между Vault —
отдельная операция, описанная в [руководстве по миграции](migration.md).

## Установка и проверка после обновления

1. Сохраните действующие версии chart, digest образов, values и UID/generation заявок.
   Для требуемой проверки неизменности данных нужен снимок **до** обновления. Хеши
   содержимого и metadata храните отдельно от значений секретов, с ограниченным доступом.
2. Проверьте [предусловия установки](installation.md), существующий manager auth и TLS.
   Установите согласованные CRD и версии всех трёх операторов через штатный источник
   desired state вашей установки. Не смешивайте новый S3 image со старой схемой,
   срезающей `pendingCreate`; не обходите GitOps прямой правкой Deployment.
3. Дождитесь завершения rollout. Сверьте фактические imageID с опубликованными digest,
   Ready/Available и актуальную observedGeneration. Проверьте discovery `vscl`.
4. Сверьте прежние UID и generation заявок. Для Ready проверяйте generation условия;
   отказ имеет свой reason и может не обновлять status последнего успешного прохода.
   Отсутствие новых Warning и ошибок не заменяет проверку состояния ресурсов.
5. На спокойном интервале проверьте [метрики](monitoring.md), reset счётчиков, requeue,
   RSS, новые токены и стабильность Pod/leader. Частота для всей группы контроллера —
   средняя по группе, а не доказательство одинакового числа проходов каждой заявки.
6. Проверьте потребителя: вход под ожидаемым SA, доступ только к собственному leaf,
   положительный доступ и отрицательные проверки соседнего ресурса. Для S3 отдельно
   проверьте чтение/запись, отказ чужим ключам, Purge собственного ресурса и сохранность
   соседнего. Успешный Ready не заменяет эти операции.

Безопасные команды чтения (подставьте свой контекст и namespace):

```sh
kubectl --context "$CONTEXT" api-resources --api-group=vault.in-cloud.io
kubectl --context "$CONTEXT" get vaultclaims,s3bucketclaims,vaultsecretclaims -A
kubectl --context "$CONTEXT" -n "$NAMESPACE" get deployment "$DEPLOYMENT"
kubectl --context "$CONTEXT" -n "$NAMESPACE" rollout status deployment/"$DEPLOYMENT" --timeout=15m
```

Если удаление не завершается, сначала установите владельца и фактическое состояние
провайдера. Ошибка доступа, transport error или `NoSuchKey` не доказывают отсутствие
бакета. Не снимайте finalizer и не удаляйте неизвестный ресурс для получения зелёного
статуса. CM может сохранять записи REMOVED: это отличается от пустого списка и должно
учитываться в проверке отсутствия активных сирот.

## Откат и известные ограничения

[Шлюз отката на v0.0.9](rollback.md) обязателен: старый оператор не умеет безопасно
обслуживать гостевые/Owned-заявки, новые поля шаблонных ролей и часть конфигураций,
которым новый выпуск отказал. Наличие таких заявок запрещает простой возврат старого
образа. Изолированный тест совместимости не даёт разрешения откатывать живую установку
с этими полями.

Возврат версии выполняется через тот же источник desired state с сохранёнными values
и digest, после проверки текущего состояния. Нельзя автоматически понижать CRD так,
чтобы API-сервер срезал необходимые status-поля. План должен включать возврат к проверенной
версии, ожидание Ready и сверку ресурсов после обеих операций.

При legacy rollback содержимое проверенных KV остаётся тем же, но старый S3/VSC может
записать новую версию того же значения. Это измеренный эффект; равенство байтов не
означает равенства счётчика версий. Отдельно различайте откат VaultClaim v0.0.9 и
legacy S3/VSC v0.0.8. Реальный provider lifecycle не подменяется fakeCM из isolated-теста.
