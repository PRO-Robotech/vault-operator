# s3-sweeper — уборщик бакетов прогонов CI

Прогон CI в kind заказывает настоящие бакеты через `S3BucketClaim`. Финализатор
заявки снимает бакет, только пока кластер жив: задание, оборванное до снятия
заявок (отмена, срок, гибель узла kind), оставляет бакет в облаке навсегда.
`s3-sweeper` убирает такие бакеты снаружи кластера.

Код — `internal/s3sweeper`, бинарь — `cmd/s3-sweeper`, образ —
`Dockerfile.s3-sweeper`, собирается заданием `docker-build.yml` как
`<namespace>/s3-sweeper:<ветка>-<sha8>`.

## Что считается бакетом прогона

Заявка прогона ставит `clusterRef.name: ci-<номер задания>`, а заявка
registry-operator с префиксом ссылки `ci-<номер задания>` — ещё и ссылку
бакета после номера: девять знаков hex и букву `a`..`p` (прежняя форма —
тринадцать цифр). Служба даёт бакету имя `<hex>-k8s-<логин>-<clusterRef.name>`,
а при занятом имени — `…-<N>`. Бакет снимается, только если **оба** условия
выполнены на строке перечня:

- владелец (`cust_login`) равен логину;
- имя целиком подходит под
  `^[0-9a-f]+-k8s-<логин>-ci-<номер>(-[0-9a-f]{9}[a-p])?(-[0-9]+)?$`.

Префикс `<hex>` принадлежит логину и может смениться после снятия последнего
бакета логина, поэтому сопоставление идёт по форме, а не по значению. Имена
вне формы не трогаются никогда: у того же логина живут чужие бакеты.

Пустой `cust_login` — известная форма ответа службы — владельцем не считается.
Строка нашей формы без владельца (не `REMOVED`) не снимается ни запуском, ни
планом `--dry-run`: она названа в журнале записью `row without owner, kept`, а
исход красный (код 1). В `sweep` задание такой строки у API CI не
спрашивается — строка не наша. Чья она, решает человек.

## Режимы

```
s3-sweeper job   --login <L> [--login <L2>] --job-id <N>     [общие флаги]
s3-sweeper sweep --login <L> [--login <L2>] --job-alive <URL> [общие флаги]
```

| режим | что снимает |
|---|---|
| `job` | бакеты задания `N`; для `after_script` / `trap EXIT` задания |
| `sweep` | бакеты заданий, которые API CI называет завершёнными (`success`, `failed`, `canceled`, `skipped`); для расписания |

`--job-alive` — адрес API CI одного задания с `{job}` на месте номера, только
`https`, без учётки в адресе. Токен — переменная `S3_SWEEPER_GITLAB_TOKEN`
(заголовок `PRIVATE-TOKEN`) либо `CI_JOB_TOKEN` (`JOB-TOKEN`). Перенаправления
не исполняются. Задание идущее (`running`, `pending` и прочие живые статусы) не
трогается; задание, которого API не знает, или статус вне словаря — бакеты не
трогаются, исход красный.

Общие флаги:

| флаг | умолчание | смысл |
|---|---|---|
| `--cloud-manager-addr` | `$CLOUD_MANAGER_ADDR` | адрес cloud-manager; в коде не зашит |
| `--dry-run` | выкл. | печатает план (`plan` с `action` = `remove` / `wait` / `none`), ничего не снимает |
| `--timeout` | `5m` | сколько ждать `REMOVED` у всех целей |
| `--poll-interval` | `10s` | пауза между перечнями |
| `--max-removals` | `20` | целей больше — отказ без единого снятия |
| `--call-timeout` | `15s` | срок одного вызова cloud-manager |

## Как идёт снятие

`removeBucket` асинхронный: принятое снятие переводит бакет в `REMOVING`, а
`REMOVED` видно лишь повторным `findAll`. Поэтому каждый проход перечисляет
бакеты логина заново:

- `RUNNING`, `ERROR`, `STOPPED` — снять (ответы `Already removed` и `Not found`
  конечные);
- `CREATING` — ждать: создание идёт, снятие следующим проходом;
- `REMOVING` — ждать, снятие не повторяется;
- `REMOVED` — готово.

## Код выхода и журнал

| код | исход |
|---|---|
| 0 | целей вне `REMOVED` не осталось (или план напечатан) и строк нашей формы без владельца нет |
| 1 | по сроку осталась цель в `RUNNING` / `REMOVING`, перечень не прочитан, предел снятий превышен, задание не классифицировано, есть строка нашей формы без владельца |
| 2 | неверный вызов: нет адреса, логина, номер задания не число, шаблон адреса API не годен |

Журнал — JSON в stderr: логин, имя бакета, статус, действие и знаменатель
`rows` (сколько строк перечня прочитано). Ключей бакетов в журнале нет —
перечень их не несёт, — и нет адресов: отказ транспорта называется кодом
gRPC или видом, а не текстом.
